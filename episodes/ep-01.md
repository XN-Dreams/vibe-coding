# Episode 1 — Zero to deployed

**Shipped:** the [roadmap](../docs/roadmap.md), 65 [glossary terms](../docs/glossary.md), and the
site, live at <https://xn-dreams.github.io/vibe-coding/>. Source: <https://github.com/XN-Dreams/vibe-coding>.

Started with an empty folder and no git repo. Ended with a public repo, 21 passing
tests, CI that gates the deploy, and a URL anyone can open.

## What we built, in order

1. Repo skeleton, `package.json` with **zero dependencies** — every script is a plain
   `node` call against a file in this repo. Nothing installed, all episode.
2. The roadmap first, because it is readable output within the first hour and it frames
   everything after it.
3. The glossary validator, **test first** — including the rule that a `related` slug must
   point at a term that exists.
4. The markdown renderer and the build CLI. One JSON file is the source of truth; the
   markdown doc and the site's data file are both generated from it.
5. 65 terms across four categories.
6. The site: one HTML page, one stylesheet, a filter function with its own tests.
7. A dependency-free static server, GitHub Pages, and CI that runs the tests before it
   lets anything deploy.

## What broke

Recorded honestly, because the debugging is the content.

**`node --test tests/` does not mean "run the tests in that directory."** It tried to
resolve `tests` as a *module* and died with `MODULE_NOT_FOUND`. The trap: the first red
test run looked correct — it failed, and we were expecting a failure — so it read as proof
that the test was wired up. It proved nothing. The runner never reached the test file at
all. Fixed by using bare `node --test`, which auto-discovers, and by re-running the red
step properly: move the implementation aside, confirm the failure names *the implementation*,
put it back.

*A red test that fails for the wrong reason is not evidence. Read the error, not the colour.*

**A backslash got eaten writing the server.** The path-traversal regex came out as
`[/\]` instead of `[/\\]` and the file would not even parse. Rather than escape around the
problem, we deleted the regex: `path.join()` already collapses `..`, so
`path.startsWith(siteRoot)` was doing the actual work the whole time. Less code, same
guarantee, and now there is exactly one line to point at when explaining the guard.

**The traversal test passed for the wrong reason.** `curl http://localhost:8080/../package.json`
returned 404 — which looks like a refusal, and isn't. `curl` normalises the URL *before
sending it*, so the server received a plain request for `/package.json`, looked inside
`site/`, and didn't find it. The attack never arrived. Only the percent-encoded version,
`/..%2fpackage.json`, reached the server intact — and that one returned **403**, which is
the guard actually firing.

*If you had shipped on the 404, you would have shipped believing you tested something you
never tested.*

**Windows line endings would have broken CI.** Git was globally set to convert `LF` to
`CRLF` on checkout. The build compares generated file contents byte for byte, so the
Linux CI runner would have called the files stale on a fresh clone and failed the deploy —
for a reason with nothing to do with the glossary. Caught before the first push by adding
`.gitattributes` with `* text=auto eol=lf`.

## What we proved, rather than asserted

- **Idempotent:** ran `npm run build` twice, `git status` empty. The word is in the
  glossary; that was the word happening.
- **The guard can fail:** deliberately added a `related` slug pointing at nothing and
  renamed another term, then watched the build exit non-zero and name all five resulting
  breakages — including the three entries that pointed at the renamed term. A guard nobody
  has watched fail is not a guard.
- **The site is actually live:** opened the published URL and counted the terms it served.
  A green checkmark on a CI run is not a shipped page.

## Decisions taken

- **Plain HTML, no framework.** Not nostalgia — Episode 2 needs a real constraint to push
  against, so the framework question gets decided with the requirement in hand.
- **Repo under the personal account, not the org.** The org holds client work; the clean-room
  rule in this repo's `CLAUDE.md` is easier to keep when the boundary is structural.
- **One JSON source of truth.** The markdown and the site data are both generated. Nobody
  maintains the same list twice.
